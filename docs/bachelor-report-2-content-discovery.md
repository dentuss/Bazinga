## АНОТАЦІЯ

УДК 004.9

[Прізвище І. П. автора 2]. Інформаційна платформа розповсюдження мультимедійного контенту за моделлю підписки (на прикладі сервісу Bazinga). Підсистема каталогу контенту, агрегатора метаданих та потокового відео. — Пояснювальна записка до випускної кваліфікаційної роботи на здобуття бакалаврського рівня вищої освіти зі спеціальності «F3 Комп'ютерні науки» (0613 Software and applications development and analysis). — Одеса: ОТУШ, 2025.

*Об'єктом дослідження* є процеси агрегування, уніфікованого подання та розповсюдження метаданих мультимедійного контенту (коміксів, манги, аніме та серіалів) з відкритих джерел у складі інформаційної системи за моделлю підписки.

*Метою роботи* є підвищення відмовостійкості та швидкодії контентного шару системи шляхом синтезу уніфікованої інформаційної моделі контенту й застосування стратегії кешування над різнорідними відкритими джерелами в умовах неповної визначеності щодо їх доступності та форматів.

*Методи дослідження* утворені суперпозицією методів системного аналізу, об'єктно-орієнтованого моделювання, порівняльного аналізу джерел даних і проєктних рішень та експериментального випробування. Інструментальне забезпечення: платформа .NET 9 (ASP.NET Core 9) з кешуванням у пам'яті (`IMemoryCache`); клієнтський застосунок на React 18 і TypeScript 5; відкриті джерела метаданих без авторизації — Jikan v4 (MyAnimeList), akabab/superhero-api, TVMaze, Open Library.

*Результати та їх новизна.* Спроєктовано та впроваджено кешувальний агрегатор метаданих, що уніфікує різнорідні відкриті джерела в єдиній інформаційній моделі контенту, а також підсистему персональних колекцій з прив'язкою до профілю та потокового перегляду відео. Новизна полягає: у синтезі уніфікованої моделі подання різнорідного контенту (єдиний інтерфейсний елемент картки для коміксів, манги, аніме та серіалів); у застосуванні стратегії «кеш-обабіч» (Cache-Aside) з диференційованими інтервалами актуальності та обмеженням темпу звернень для обходу лімітів зовнішніх джерел; у відв'язуванні клієнта від конкретного постачальника метаданих через комунікаційні інтерфейси, що дозволило замінити припинений комерційний сервіс відкритим джерелом без зміни клієнтської частини.

*Основні характеристики.* Реалізовано єдину точку доступу до метаданих (18 ендпоінтів); статичний набір даних персонажів обсягом близько 1 МБ завантажується одноразово й обробляється у пам'яті; повторні звернення до каталогу обслуговуються з кешу за час порядку мілісекунд.

*Сфера застосування* — інформаційні системи розповсюдження цифрового контенту, агрегатори метаданих, системи е-комерції контенту. *Значущість роботи* визначається відповідністю напряму державної політики щодо розвитку цифрової економіки та інформаційного суспільства. *Взаємозв'язок з іншими роботами* — підсистема є складовою командного проєкту Bazinga; підсистема облікових записів, профілів та підписок реалізована першим виконавцем.

Пояснювальна записка складається зі вступу, технічного завдання, трьох розділів, висновків, переліку використаних джерел та додатка з лістингами програмного коду. При складанні звіту використано 22 джерела інформації.

## ВСТУП

**Оцінка сучасного стану об'єкта дослідження.** Сучасні інформаційні системи розповсюдження мультимедійного контенту дедалі частіше будуються як агрегатори, що поєднують контент і метадані з кількох джерел. Якість такого контентного шару визначає швидкість доступу до контенту, повноту його опису (обкладинки, описи, жанри) та зручність пошуку. Водночас побудова власної редакційної бази метаданих на десятки тисяч одиниць контенту є ресурсомісткою, тому поширеною є інтеграція із зовнішніми джерелами метаданих.

**Світові тенденції розв'язання задачі.** Провідні системи застосовують уніфіковане подання різнорідного контенту, наскрізний пошук за кількома категоріями одночасно, персональні колекції на рівні профілю та потоковий перегляд без завантаження файлів. На рівні інженерних рішень типовими є кешування зовнішніх звернень для зниження навантаження й затримок, а також відв'язування системи від конкретного постачальника даних задля стійкості до змін у його доступності.

**Актуальність роботи.** Розвиток систем електронної комерції контенту та цифрових послуг визначено державним пріоритетом у Стратегії розвитку інформаційного суспільства в Україні. Побудова відмовостійкого контентного шару, здатного агрегувати різнорідні джерела й зберігати працездатність за їх часткової відмови, є передумовою функціонування таких систем, що й обумовлює актуальність роботи.

**Умови невизначеності.** Задача побудови агрегатора сформульована в умовах істотної неповної визначеності: зовнішні джерела метаданих мають різні формати відповідей, накладають обмеження на темп звернень, можуть бути тимчасово недоступними, а окремі з них — узагалі припинятися. Зокрема, у ході роботи комерційний сервіс метаданих коміксів (Marvel Developer API) став недоступним, що потребувало дослідницького переходу на альтернативне відкрите джерело без зміни клієнтської частини. Це підтверджує недетермінований характер задачі та потребу проєктування під невизначеність.

**Наукова новизна.** Новизна роботи полягає у синтезі уніфікованої інформаційної моделі подання різнорідного контенту та у застосуванні стратегії кешування з обмеженням темпу звернень для обходу лімітів зовнішніх джерел. Додатковим елементом новизни є архітектурне відв'язування клієнта від постачальника метаданих через комунікаційні інтерфейси, що забезпечує підмінність джерела без модифікації решти системи. Порівняльний аналіз (розділ 1) показує, що поєднання цих властивостей вирізняє запропоноване рішення серед систем-аналогів.

**Мета і задачі.** Метою роботи є проєктування, реалізація та впровадження відмовостійкого й швидкодійного контентного шару інформаційної системи Bazinga — кешувального агрегатора метаданих, уніфікованого каталогу, персональних колекцій та потокового відео. Для досягнення мети поставлено такі задачі:

1. провести огляд інформаційних систем розповсюдження контенту та порівняльний аналіз доступних зовнішніх джерел метаданих, встановити критерії вибору й напрями удосконалення;
2. спроєктувати кешувальний агрегатор метаданих з уніфікованою інформаційною моделлю контенту та стратегією зниження кількості зовнішніх звернень;
3. інтегрувати відкриті джерела метаданих та забезпечити стійкість до їх відмови й обмежень темпу звернень;
4. реалізувати уніфікований каталог контенту, наскрізний пошук за кількома типами контенту та потоковий перегляд відео;
5. реалізувати підсистему персональних колекцій з прив'язкою до профілю користувача;
6. провести випробування підсистеми, зокрема в умовах відмови та обмежень зовнішніх джерел, та оцінити відповідність технічному завданню.

**Сфера застосування та взаємозв'язок з іншими роботами.** Результати застосовні в інформаційних системах розповсюдження контенту та агрегаторах метаданих. Робота є складовою командного проєкту; підсистема облікових записів, профілів та платіжно-підписної моделі реалізована першим виконавцем і описана в окремій пояснювальній записці.

## ТЕХНІЧНЕ ЗАВДАННЯ ДО ПРОЄКТУ

### Загальний опис

Програмне забезпечення реалізує контентний шар розподіленої інформаційної системи Bazinga — кешувальний агрегатор метаданих, уніфікований каталог коміксів, манги, персонажів і серіалів, наскрізний пошук, потоковий перегляд відео та персональні колекції користувача. Підсистема є спільною основою двох предметних складових системи — Bazinga Comics (комікси й манга) та BazingaTV (потокове відео).

### Призначення

Підсистема призначена для виконання таких користувацьких сценаріїв:

- перегляд каталогу коміксів, манги, персонажів та серіалів з обкладинками, описами й жанрами;
- наскрізний пошук одночасно за кількома типами контенту з відкриттям детального подання без переходу на іншу сторінку;
- збереження одиниць контенту до персональних колекцій («Бібліотека» для коміксів/манги та «Мій список» для відео) з прив'язкою до активного профілю;
- потоковий перегляд відеоконтенту у вбудованому програвачі;
- фільтрація та посторінкове гортання каталогу.

### Функціональні вимоги до підсистеми

**Каталог і метадані:**

- єдина точка доступу до метаданих з кількох зовнішніх джерел;
- уніфіковане подання різнорідного контенту однаковими інтерфейсними елементами;
- фільтрація за жанрами/видавцями та посторінкове гортання;
- виключення контенту для дорослих із загальнодоступних добірок.

**Пошук:**

- наскрізний пошук одночасно за коміксами, мангою, аніме та персонажами;
- відкриття детального подання результату безпосередньо в накладенні (без переходу на іншу сторінку).

**Персональні колекції:**

- збереження одиниць контенту до колекцій «Бібліотека» та «Мій список»;
- прив'язка колекцій до активного профілю (кожен профіль має власні колекції);
- розподіл колекції за типами контенту (усе / комікси / манга та усе / аніме / серіали).

**Потокове відео:**

- головна сторінка BazingaTV з добірками контенту та героїчним блоком;
- повноекранний перегляд у вбудованому програвачі.

### Нефункціональні вимоги

- кількість звернень до зовнішніх джерел мінімізується кешуванням; темп звернень не повинен перевищувати обмежень джерел;
- повторні звернення до каталогу обслуговуються з кешу за час порядку мілісекунд;
- за відмови зовнішнього джерела підсистема зберігає працездатність (порожня добірка чи резервний набір замість аварійного завершення);
- клієнтська частина адаптивна; підтримуються актуальні версії основних браузерів.

### Архітектура та технології

Серверна частина — ASP.NET Core 9 з кешуванням у пам'яті та фабрикою HTTP-клієнтів; клієнтська — React 18 + TypeScript зі складанням засобами Vite. Зовнішні джерела метаданих: Jikan v4 (MyAnimeList) — аніме й манга; akabab/superhero-api — персонажі коміксів; TVMaze — серіали; Open Library — комікси. Розгортання — Docker і Docker Compose.

## РОЗДІЛ 1. ЗАГАЛЬНА ХАРАКТЕРИСТИКА СИСТЕМИ ТА ПОРІВНЯЛЬНИЙ АНАЛІЗ

Інформаційна система Bazinga є розподіленою клієнт-серверною системою, побудованою за архітектурним стилем «односторінковий застосунок поверх комунікаційного протоколу REST». Цей розділ присвячено загальній характеристиці системи та порівняльному аналізу наявних рішень, за результатами якого обґрунтовано предмет розроблення контентної підсистеми.

Контентний шар, що є предметом цієї роботи, реалізує єдину точку доступу до метаданих, уніфікований каталог, наскрізний пошук, потоковий перегляд і персональні колекції. Серверна частина застосовує кешування у пам'яті та фабрику HTTP-клієнтів для звернень до зовнішніх джерел; клієнтська частина уніфікує подання різнорідного контенту спільними інтерфейсними компонентами.

**Порівняльний аналіз наявних рішень.** Для обґрунтування предмета розроблення проведено порівняння інформаційних систем-аналогів за ознаками, що стосуються виявлення та споживання контенту. Результати наведено у таблиці 1.1.

Серед систем-аналогів персональні колекції на рівні профілю реалізовано лише в Netflix, який і взято за взірець щодо цієї властивості. Водночас жодна з наявних систем не поєднує єдиного каталогу різнорідного контенту з наскрізним пошуком, уніфікованим поданням та незалежністю від конкретного джерела метаданих — саме усунення цих «мінусів» становить предмет удосконалення.

**Міні-висновок за розділом.** Встановлено, *що* розробляється — відмовостійкий контентний шар з уніфікованим поданням різнорідного контенту й незалежністю від конкретного джерела метаданих; *чому* не застосовано готове рішення — наявні системи орієнтовані на один тип контенту й не передбачають підмінності джерел; *для чого* це потрібно — побудова такого шару є передумовою функціонування інформаційної системи розповсюдження контенту за підпискою. Це обґрунтовує предмет і задачі подальшого проєктування.

## РОЗДІЛ 2. ПРОЄКТУВАННЯ ТА РЕАЛІЗАЦІЯ ПІДСИСТЕМИ

Розділ присвячено проєктним рішенням та їх реалізації. Викладено порівняльний вибір зовнішніх джерел метаданих, проєкт кешувального агрегатора, інтеграцію джерел, комунікаційні інтерфейси, підсистему персональних колекцій та клієнтську частину. Фрагменти коду винесено у додаток А із посиланнями за текстом.

### 2.1. Порівняльний вибір зовнішніх джерел метаданих

Вибір джерел виконано методом порівняльного аналізу за критеріями: відсутність обов'язкової авторизації, наявність обкладинок, описів і жанрів, обмеження темпу звернень та стабільність доступу. Результати наведено у таблиці 2.1.

Таблиця 2.1 — Порівняльний аналіз джерел метаданих

| Джерело | Без авторизації | Обкладинки | Описи/жанри | Стабільність доступу |
|---|:---:|:---:|:---:|:---:|
| Marvel Developer API | – | + | + | – (припинено) |
| ComicVine | – | + | + | + |
| TMDB | – | + | + | + |
| Jikan v4 (MyAnimeList) | + | + | + | + |
| akabab/superhero-api | + | + | +/– | + |

За результатами аналізу для аніме й манги обрано Jikan v4, для персонажів коміксів — akabab/superhero-api, для серіалів — TVMaze, для коміксів — Open Library. Джерела, що потребують авторизації або підпису кожного звернення (Marvel, ComicVine, TMDB), відхилено; додатковим підтвердженням ризику залежності від комерційного джерела стало припинення доступу до Marvel Developer API під час виконання роботи, після чого джерело коміксів було замінено на Open Library без зміни клієнтської частини — завдяки відв'язуванню через комунікаційні інтерфейси (п. 2.3).

### 2.2. Кешувальний агрегатор метаданих

Агрегатор спроєктовано за стратегією «кеш-обабіч» (Cache-Aside) над кешем у пам'яті. Для уникнення дублювання коду застосовано узагальнений (generic) метод кешованого посторінкового отримання даних, параметризований сирим типом постачальника та власним типом моделі (лістинг А.1). Інтервали актуальності диференційовано за характером даних: списки — короткий інтервал, деталі — середній, статичні набори — тривалий.

Зовнішнє джерело Jikan накладає обмеження темпу звернень (близько трьох на секунду). Під час одночасного формування кількох добірок частина звернень відхилялася із кодом «занадто багато запитів», унаслідок чого окремі ряди залишалися порожніми. Для усунення цього синтезовано механізм обмеження темпу звернень: звернення серіалізуються процесним семафором із мінімальним інтервалом між ними та одним повтором після паузи у разі відхилення (лістинг А.2). Це гарантує дотримання обмежень джерела без втрати даних.

Для виключення контенту для дорослих із загальнодоступних добірок реалізовано фільтр жанрів манги, що доповнює недостатній штатний параметр джерела (лістинг А.3).

### 2.3. Інтеграція джерела коміксів (Open Library)

Джерело коміксів інтегровано через комунікаційний інтерфейс `IComicMetadataService`, реалізація якого `OpenLibraryComicService` звертається до відкритого API Open Library. Базову добірку сформовано як об'єднання курованих запитів за супергеройськими франшизами з усуненням повторів та чергуванням джерел (лістинг А.4); вільнотекстовий пошук обмежено предметною рубрикою коміксів. Сирі відповіді відображаються в уніфіковану модель: побудова адрес обкладинок, виокремлення авторів і року, очищення переліку жанрів (лістинги А.5, А.6). Завдяки реалізації через інтерфейс заміна джерела не торкається ані комунікаційного контролера, ані клієнтської частини.

### 2.4. Комунікаційні інтерфейси (контролери)

Єдину точку доступу до метаданих реалізовано контролером `MetadataController`, який надає ендпоінти за всіма категоріями контенту — аніме, манга, персонажі, серіали та комікси (лістинг А.7). Контролер залежить від інтерфейсів сервісів (`IJikanService`, `ISuperheroService`, `IComicMetadataService`), а не від конкретних реалізацій, що відповідає принципу інверсії залежностей. Сервіс персонажів після одноразового завантаження статичного набору виконує фільтрацію та посторінкове гортання повністю у пам'яті (лістинг А.8).

### 2.5. Підсистема персональних колекцій

Персональні колекції реалізовано окремою структурною сутністю, відв'язаною від таблиці локальних коміксів, що дозволяє зберігати одиниці контенту з будь-якого зовнішнього джерела. Колекції прив'язано до профілю: активний профіль визначається із заголовка звернення та звіряється з власником облікового запису (лістинг А.9). Це реалізує вимогу «кожен профіль має власні колекції». Дві колекції — «Бібліотека» (комікси й манга) та «Мій список» (аніме й серіали) — розрізняються дискримінатором, що зменшує кількість структурних сутностей.

### 2.6. Клієнтська частина

Клієнтську частину побудовано навколо уніфікованого подання контенту. Єдиний компонент картки відображає однаково комікси, мангу, аніме та серіали; за відмови завантаження обкладинки застосовується градієнтний замінник із назвою, що зберігає цілісність сітки (лістинг А.11). Горизонтальні ряди підтримують дворядкове подання та гортання кнопками (лістинг А.13). Наскрізний пошук виконує паралельні звернення за кількома типами контенту з усуненням «миготіння» введення (debounce) і відкриває детальне подання безпосередньо в накладенні; для коректного позиціонування накладення винесено у портал кореневого вузла документа (лістинг А.12). Контекст персональних колекцій перезавантажується при зміні активного профілю, що й забезпечує окремі колекції для кожного профілю (лістинг А.10). Потоковий перегляд реалізовано вбудованим програвачем стандарту HTML5 без сторонніх залежностей.

## РОЗДІЛ 3. ВИПРОБУВАННЯ ТА ОЦІНКА РЕЗУЛЬТАТІВ

Розділ присвячено перевірці підсистеми після першого успішного запуску: відповідності технічному завданню, функціональному випробуванню, перевірці відмовостійкості та обходу обмежень зовнішніх джерел, оцінці продуктивності й засобам контролю якості.

### 3.1. Відповідність технічному завданню

Перевіркою проходженням сценаріїв підтверджено реалізацію всіх функціональних вимог: єдиної точки доступу до метаданих; уніфікованого каталогу з фільтрацією та гортанням; наскрізного пошуку за кількома типами контенту з відкриттям деталей у накладенні; персональних колекцій на рівні профілю; потокового перегляду відео.

### 3.2. Функціональне випробування

Перевірено: наповнення всіх рядів каталогу реальними метаданими (обкладинки, описи, жанри); коректне розділення персональних колекцій між профілями (перемикання профілю змінює вміст «Бібліотеки» та «Мого списку»); відкриття деталей результату пошуку в накладенні без переходу на іншу сторінку; виключення контенту для дорослих із загальнодоступних добірок.

### 3.3. Випробування відмовостійкості та обходу обмежень

Підтверджено усунення проблеми порожніх рядів: після впровадження обмеження темпу звернень добірки, що формуються одночасно, наповнюються повністю, оскільки звернення більше не відхиляються джерелом за перевищення темпу. Перевірено градаційне зниження функціональності: за недоступності зовнішнього джерела підсистема повертає порожню добірку чи резервний набір замість аварійного завершення. Окремо підтверджено сценарій підміни джерела: після припинення доступу до комерційного сервісу коміксів джерело замінено відкритим без зміни клієнтської частини, що засвідчує коректність відв'язування через комунікаційні інтерфейси.

### 3.4. Оцінка продуктивності

Повторні звернення до каталогу обслуговуються з кешу за час порядку мілісекунд, без звернень до мережі. Статичний набір даних персонажів (близько 1 МБ) завантажується одноразово й кешується на тривалий інтервал, після чого пошук, фільтрація та гортання виконуються у пам'яті. Завдяки мінімальному інтервалу між зверненнями до Jikan дотримується обмеження темпу джерела навіть під час інтенсивного гортання.

### 3.5. Контроль якості та командна взаємодія

Розроблення велося із застосуванням системи контролю версій Git за моделлю гілок, запитів на злиття та взаємного рецензування коду. Типобезпеку перевіряв компілятор TypeScript, складання — засоби Vite, стиль коду — статичний аналізатор. Інтеграцію з підсистемою облікових записів здійснено через узгоджені комунікаційні інтерфейси та спільний контекст автентифікації.

### 3.6. Підсумкова оцінка

Функціональність, передбачена технічним завданням, реалізована повністю. Контентний шар забезпечує уніфіковане подання різнорідного контенту, наскрізний пошук, персональні колекції та потоковий перегляд, зберігаючи працездатність за відмови чи обмежень зовнішніх джерел. Обрані рішення підтвердили доцільність; підсистема є придатною до підміни й розширення джерел метаданих без модифікації клієнта.

## ВИСНОВКИ

У ході виконання випускної кваліфікаційної роботи спроєктовано та впроваджено відмовостійкий контентний шар інформаційної системи Bazinga. Висновки за поставленими у вступі задачами наведено нижче.

- **Задача 1 (огляд і порівняння).** Проведено огляд систем розповсюдження контенту та порівняльний аналіз як споживчих систем (таблиця 1.1), так і доступних джерел метаданих (таблиця 2.1). Встановлено критерії вибору джерел і визначено предмет удосконалення — уніфіковане подання різнорідного контенту з незалежністю від конкретного джерела.

- **Задача 2 (агрегатор).** Спроєктовано кешувальний агрегатор за стратегією Cache-Aside з диференційованими інтервалами актуальності та узагальненим методом кешованого гортання, що усунув дублювання коду між однотипними методами.

- **Задача 3 (інтеграція й стійкість).** Інтегровано чотири відкриті джерела метаданих без авторизації; синтезовано механізм обмеження темпу звернень, що усунув відхилення звернень за перевищення лімітів і пов'язану з ним проблему порожніх рядів; забезпечено градаційне зниження функціональності за відмови джерел.

- **Задача 4 (каталог, пошук, відео).** Реалізовано уніфікований каталог зі спільним компонентом подання різнорідного контенту, наскрізний пошук за чотирма типами контенту з відкриттям деталей у накладенні та потоковий перегляд відео вбудованим програвачем HTML5.

- **Задача 5 (персональні колекції).** Реалізовано підсистему персональних колекцій («Бібліотека» та «Мій список») з прив'язкою до профілю; підтверджено, що кожен профіль має власні колекції.

- **Задача 6 (випробування).** Проведено функціональне випробування й перевірку відмовостійкості; підтверджено наповнення рядів після впровадження обмеження темпу звернень, обслуговування повторних звернень з кешу за час порядку мілісекунд та коректність підміни джерела без зміни клієнта.

Наукова новизна роботи полягає у синтезі уніфікованої інформаційної моделі подання різнорідного контенту та у застосуванні кешування з обмеженням темпу звернень й відв'язуванням від постачальника метаданих, що забезпечує відмовостійкість в умовах неповної визначеності. Практична цінність визначається застосовністю результатів у системах розповсюдження контенту та агрегаторах метаданих, розвиток яких є державним пріоритетом.

Перспективними напрямами подальших досліджень є впровадження адаптивного потокового відео (HLS/DASH), застосування мережі доставки контенту (CDN) для статичних ресурсів та побудова рекомендаційної підсистеми на основі колаборативної фільтрації.

Лістинг А.2 — Обмеження темпу звернень до зовнішнього джерела з одним повтором (`Services/JikanService.cs`)

```csharp
// Серіалізуємо звернення процесним семафором із мінімальним інтервалом, щоб
// не перевищувати ~3 запити/с і не отримувати відмов «занадто багато запитів».
private static readonly SemaphoreSlim Gate = new(1, 1);
private static readonly TimeSpan MinSpacing = TimeSpan.FromMilliseconds(380);
private static DateTime _lastCallUtc = DateTime.MinValue;

private async Task<HttpResponseMessage> SendThrottledAsync(string path, CancellationToken ct)
{
    await Gate.WaitAsync(ct);
    try
    {
        var since = DateTime.UtcNow - _lastCallUtc;
        if (since < MinSpacing) await Task.Delay(MinSpacing - since, ct);
        try { return await _http.GetAsync(path, ct); }
        finally { _lastCallUtc = DateTime.UtcNow; }
    }
    finally { Gate.Release(); }
}

private async Task<T?> GetJsonAsync<T>(string path, CancellationToken ct)
{
    for (var attempt = 0; attempt < 2; attempt++)
    {
        using var resp = await SendThrottledAsync(path, ct);
        if (resp.StatusCode == System.Net.HttpStatusCode.TooManyRequests)
        {
            if (attempt == 0) { await Task.Delay(TimeSpan.FromMilliseconds(900), ct); continue; }
            return default;
        }
        if (!resp.IsSuccessStatusCode) return default;
        return await resp.Content.ReadFromJsonAsync<T>(Json, ct);
    }
    return default;
}
```
